# HASH160 evidence (2026-10-17)

Every verdict is the independent verifier `../p6/verify_htlc.py` (stdlib only; it recomputes RIPEMD160(SHA256(preimage)) itself and queries the chain), not the program's own output.

1. **Does the chain and a published SDK accept HASH160 at all?** `p0-python-published-probe.log` (`htlc_ref_hash160.py`, PyPI `accumulate-sdk-opendlt` 2.5.0): lock accepted, deposit found, release accepted, receiver 700000000 to 800000000. Verifier: `python-probe-positive.json` (PASS, 15/15).
2. **Generated programs, all five languages, published registry versions.** One run each, started together. Every run PASS 16/16 and the on-chain send header carries `hashAlgorithm hash160` with a 20-byte hash. `<lang>-hash160-1.json` are in `../e2e/`, the full program logs in `../e2e/logs/`.
3. **Wrong preimage with a HASH160 lock fails on the node.** `p0-python-wrong-preimage-hash160.log` (exit 1, "preimage does not match hash (unauthenticated, code 401)"); verifier `python-wrong-hash160.json` (PASS, 11/11, negative mode: the deposit stays locked and the receiver is unchanged). The first invocation used the verifier's default starting balance (0) although that reference program pre-funds its receiver with 700000000, so one check failed on that parameter, not on the chain: kept as `python-wrong-hash160-default-before-0.json`.
4. **Compile proof, five languages, against the real dependencies** (`ripemd` 0.1.3, `pointycastle`, `BouncyCastle.Cryptography` 2.7.0): `compile-all-5-languages.txt`.
5. **Mock execution in the five validation suites** (the generated program runs against the faithful node mock, which judges the lock and the release with RIPEMD160(SHA256)): `validation-suites.txt`.
